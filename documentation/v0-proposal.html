Agent Advocate

An evidence-based second view that helps a coding coordinator notice delivery problems, choose a useful response, and retain the lessons that still matter.

v0: five skills, a private SQLite store, and a simple timer. Step 1 has a preserved unmerged candidate; required-review readiness comes first.

What I heard

Builds can spend too long expanding scope, repeating checks, or cycling through reviews. The coordinator needs timely evidence and informed advice before work, at normal checkpoints, and after the outcome is known.

The approved direction is to build a useful v0 quickly, use it during selected v1 work, and then resume the separately approved Skill Mesh improvements. Existing useful work supplies the live example; no benchmark project is required.

The September 23 correction puts the recurring review-capability failure first. Repair the shared adapter in its owning project; teach Agent Advocate to detect unsupported gates, missing helpers and capacity mismatches before recommending a build.

Why this shape

Before work

assign-advocate checks required review capability against loaded adapters, packaged helpers and actual host tools. It records available, unavailable or unknown with evidence, then obtains an independent assessment when possible.

At checkpoints

status-inquisition checks progress neutrally. coordination-cowbell investigates a suspected problem. A missed expectation signals overdue visibility, not proof of failure.

After work

advocate-wrap records the outcome, identifies the owning component, and retires obsolete cautions. model-mother deliberately refreshes dated, scoped model guidance.

The timer checks deadlines every 60 seconds by default. It records deduplicated alerts in a visible watch terminal. Model-assisted diagnosis happens when a skill is invoked; the timer never launches models or stops builds.

Build timeline

  1. First · Repair the shared review prerequisite

    Existing Skill Mesh Phase CD adds conditional Codex dispatch, the missing code-lane resources, and capacity-limited batches of six fresh independent reviewers. Qualify the generated install and refresh the actual profile before relying on it.

    This is an owning-component repair, not another Agent Advocate code step. Preserve the existing Step 1 candidate, findings and retry history.

  2. Step 1 · Durable run and evidence

    Build the Python CLI and SQLite lifecycle. Prove persistence with fresh processes, retry identity, bounded concurrent writes, and the external private-store boundary.

    Produces a usable local utility. Deep review targets the persistent schema.

  3. Step 2 · Five working skill packages

    Add project-local Codex packages, shared instructions, public-source cautions, and relevant-pattern retrieval. Prove package structure and helper behavior; native execution is observed in M1.

    Uses ordinary code review. No Skill Mesh installation is a dependency.

  4. Step 3 · Timer and alerts

    Add the foreground watchdog, persistent deduplication, snooze/acknowledgment, pause/resume, and an exact acceptance runbook. Prove the watcher/store boundary using a short real process test.

    Deep review targets timer/persistence behavior. No long soak is required.

  5. M1 · Live acceptance

    In a fresh Codex session, observe all five skills, actual independent assessment and web research, persisted observations, and the watcher across two normal intervals plus a short overdue case.

    Observed product behavior qualifies v0; long-term productivity benefit remains unproven.

Afterwards

Once the required route is qualified and build ownership reconciled, resume here with /build-phase --plan plan.md --steps 1,2,3 --resume 1. After the code steps, run M1. The handoff preserves the prior candidate and does not reset repair rounds.

Once implemented: uv sync --locked, then uv run --locked agent-advocate init. Invoke $assign-advocate in Codex and use its returned run UUID with agent-advocate watch.

Agent defaults

These implementation details fit the approved scope. They do not require another approval round.

D1 · Stack

Standard-library Python

What: Python 3.12+, uv, pytest for development, setuptools packaging.

Why: Built-in SQLite and process tools cover the utility without runtime dependencies.

Tweak: Introduce a dependency only for a concrete unmet requirement.

D2 · Privacy

External per-user store

What: Keep database and evidence outside Git; no public runtime exporter.

Why: A public codebase must not accidentally publish private run records.

Tweak: Override the local data directory; keep the Git-tree refusal.

D3 · Discovery

Project-local Codex skills

What: Discover skills from this checkout and explicitly name monitored project paths.

Why: Start using v0 without an installer or external catalog dependency.

Tweak: Qualify broader installation and Claude support in later work.

D4 · Delivery

Three code slices and one observation

What: Persistence, skills, watchdog, then M1.

Why: Each slice has concrete acceptance; live host behavior is observed separately.

Tweak: Split only if implementation exposes a real dependency or scope problem.

D5 · Monitoring

Explicit checkpoints

What: Skills submit progress; the timer raises deterministic advisory alerts.

Why: Avoid guessing activity from transcripts or paying for a model every poll.

Tweak: Add automatic diagnostic dispatch only after useful real evidence supports it.

D6 · Context

Five relevant cautions at most

What: Retrieve applicable active patterns, retaining hypothesis labels.

Why: Historical advice should not overwhelm the actual task.

Tweak: Adjust the retrieval limit and ranking after observed use.

D7 · Ownership

Repair once; detect early

What: Repair Skill Mesh's shared engine through its existing Phase CD plan. Agent Advocate records readiness using its existing Observation fields.

Why: A second review engine or another capability database would duplicate the problem's owner.

Tweak: Extend the same preflight evidence to other required gates after real incidents.

D8 · Bounded resume

Stop before validation becomes the project

What: The next Steps 1-3 invocation gets 90 minutes total and at most five minutes of cumulative test execution per step. Review the preserved Step 1 candidate first; retain retry history and required gates.

Why: A limit on repeat count did not control the observed cost. These agent-selected limits are execution bounds, not completion promises.

Tweak: Reaching a bound checkpoints and stops; changing a limit requires an explicit subsequent decision, not automatic extension.

Deferred beyond v0

Claude qualification, automatic timer-to-diagnostic dispatch, richer test/review receipt ingestion, Switchboard inventory reads, an optional observatory summary, and wider skill installation are v1 candidates. A dashboard, new model API client, automatic fixer, and multi-hour productivity study are outside this v0.

Risks and limits

  • Checkpoint claims can be wrong. Independent assessments need primary evidence and actual provenance.
  • Overdue visibility can mean legitimate waiting. Alerts preserve state, reason and uncertainty.
  • Local storage is not encryption or a promise of offline model reasoning. The active host's account policies still apply.
  • A saved alert can go unprinted if a process crashes at the output boundary. Startup/status exposes unresolved alerts.
  • A host may lack agents or web tools. Record unavailable capability; do not mark live acceptance complete.
  • A correction applied is not proof of benefit. Wrap preserves that distinction and retires unhelpful cautions.
